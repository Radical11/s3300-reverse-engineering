# Executable placement and hook contracts

25 October 2026. This investigation deepens the remaining executable-readiness
gates. It emits no patch, firmware candidate or device command. Reproducible
metadata is in `evidence/executable-contracts.json`, generated by
`tools/map_executable_contracts.py`.

The source is the authenticated supplied v1.1 carrier and its authenticated
application ELF. Sixteen direct Ghidra dossiers are independently byte-checked
against that ELF, alongside 34 exact instruction assertions. These are static
Ghidra/Capstone findings, not native REA Evidence or camera execution.

## Startup memory has owners

The application entry **0x80000600** initializes **gp=0x8010ef80** and
**sp=0x809f2168**, then jumps to continuation **0x800006c0**. That continuation
checks CP0 EBase low ten bits. When they are not one, it invokes the reviewed
memset-like routine **0x800efc30** to clear:

| Range, end exclusive | Bytes | Consequence |
| --- | ---: | --- |
| 0x8089c880–0x809f1574 | 1,395,956 | Runtime-zeroed state; absent source bytes do not make this free placement |
| 0x80106ff0–0x80107608 | 1,560 | Most of an apparent gap is explicitly initialized at startup |

The second mapped interval ends at 0x80107680, leaving only an unexplained
0x78-byte remainder after the zeroed part. That remainder is still **not a
verified free region**. Other unbacked gaps are recorded without inventing
bytes or a loader allocation. The large zeroed state follows the last decoded
application region exactly, at 0x8089c880.

RTOS initializer **0x800ce7c8** selects a 0x1000-byte timer-stack range:

| CP0 context selection | State object | Timer-stack range |
| --- | --- | --- |
| low ten bits equal zero | 0x800d1ad4 | 0x809f3178–0x809f4178 |
| nonzero | 0x800d4b34 | 0x809f2178–0x809f3178 |

It stores the existing stack pointer at state+0, the timer-stack base at+0x248,
length at+0x24c, and end at+0x1a8. The boot route later passes this end to the
allocator. This does not identify the actual core count, prove every nonzero
context executes, or establish the entire stack policy. Ghidra decodes two
shadow-register instructions in this routine that the current Capstone profile
does not fully decode; their bytes are checked independently rather than
claiming complete Capstone support.

Allocator initializer **0x80020804** queries DRAM size through **0x8003c3ac**
and requests a pool via **0x800205a4** using:

```
pool_start = incoming_start & 0xdfffffff
pool_length = queried_DRAM_bytes - (incoming_start & 0x0fffffff) - 4
```

The arithmetic is 32-bit unsigned. Live DRAM size and remaining allocator
headroom are not read in this pass. The pool is already owned by the running
allocator; obtaining a heap pointer would not by itself establish executable
permission, loader retention or a safe place for code.

Subpool initializer **0x80020768** defaults to 0x380000 bytes when its argument
is zero. The reviewed boot caller instead obtains **0x1c2000** from getter
**0x80000d38** and forwards it as an override. Another subpool request is
0x180000 bytes with a 0x200-sized unit hint. These are requested pool
configurations, not a measurement of free memory or overall installed RAM.

## Cache publication needs a complete sequence

The native index exposes useful source-checked cache routines:

| Entry | Address/length behavior and observed CACHE code | Status |
| --- | --- | --- |
| 0x800b43bc | a0=address, a1=length; null/zero asserts; operation 0x10 | I-cache invalidation path |
| 0x800b3a9c | a0=address, a1=length; null/zero asserts; operation 0x11 | D-cache invalidation path |
| 0x800b52e4 | a0=address, a1=length; null/zero selects a whole-cache fallback; operation 0x15 | D-cache writeback/invalidation candidate |
| 0x800b4614 | a0=address, a1=length; operation 0x19 | D-cache writeback candidate; full invalid-input policy unestablished |

Reviewed address arithmetic masks with 0xdfffffff, aligns downward using
runtime line-exponent state and iterates until address+length. Larger requests
can use tag scans. Cache geometry is initialized from CP0 Config1 in
**0x800b3680**, and is not known solely from these instructions. The routines
also call context/timing helpers **0x800b22fc/0x800b2364**; they are not passive
memory accessors. No public SDK wrapper is added for them.

Finding these entries does not establish the required order, cross-context
visibility, DMA completion, barriers, interrupt ownership or safe execution
handoff after loading new code. The code-publication gate remains closed.

## Calls and hooks require instruction-level contracts

The main application header declares ELF32 little-endian MIPS32r2/o32,
flags **0x70001001**, without a `.MIPS.abiflags` record. The generated SDK's
soft-float declaration is our integer-only build choice, not a recovered vendor
floating-point ABI.

The mapper checks real JAL sites and their delay slots. For example,
**0x80020844** calls the DRAM query while its delay slot writes zero to
**sp+0x10**; that slot is part of the argument/setup contract. JAL writes its
link as **PC+8**. Direct J/JAL combines its encoded low 28 bits with the high
four bits of **PC+4**. Therefore the SDK's synthetic address **0x10000** cannot
be reached by one direct J/JAL from the application's **0x8xxxxxxx** region.
No call-site encoder or automatic trampoline is produced by this mapper.

Ordinary conditional branches have signed 16-bit word displacements from
PC+4. Branch-likely instructions additionally annul the delay slot when not
taken. Displaced branches, delay slots, live register values, stack alignment,
saved registers, return state and the firmware gp value must be handled for
the selected hook—not assumed from a successful host compilation.

The capture entry candidate **0x80205918** begins by preserving a0 in t4
before pointer checks and stack allocation. The earlier **0x80205924** address
is an interior stack-allocation instruction. The final native inventory does
not have an independently discovered function entry at 0x80205918; its use
remains based on a reviewed instruction window. This matters for automatic
hook selection. The tiny loader's odd entry **0x81000401** and distinct flags
**0x10001000** require separate instruction-mode recovery; the main application
profile must not be imposed on it.

## No free code cave has been proved

The scan finds **643 runs of at least 32 zero bytes** in regions marked
executable by the authenticated ELF metadata. Its largest 32 are retained
with addresses, sizes and whether native function entries occur inside them.
ELF executable permission, zeros, absent function entries and unbacked gaps
do not prove unused storage, startup ownership, persistent loader coverage or
runtime execution safety. There are **zero approved placements**.

Executable trials remain blocked on a placement with demonstrated ownership,
complete hook/calling state, a validated cache/publication sequence and
software recovery independent of a functioning modified application. The
successful SDK compile/emulation and the observed Amber data modification do
not satisfy those gates.
