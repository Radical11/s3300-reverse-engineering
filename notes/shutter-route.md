# Capture-mode arm to saved-JPEG processing

25 October 2026. Status: **partial static contract; no camera-callable adapter**.
This map connects an application UI capture arm to the existing saved-image
pipeline. It does not establish the physical shutter producer or observe live
Auto-mode state. No camera request, mode change or firmware patch was performed.

The reproducible report is [shutter-route.json](../evidence/shutter-route.json),
generated by [map_shutter_route.py](../tools/map_shutter_route.py). It authenticates
the supplied v1.1 firmware and decoded image, checks 53 selected instructions
with independent Capstone, corroborates all instructions in 14 retained direct
Ghidra dossiers, and checks two analyst-bounded thread windows. Direct Ghidra
findings remain separate from REA Evidence. Windows without a native dossier
are not promoted to authenticated function boundaries.

## UI setup and capture-mode selection

UI handler `80707590` calls setup `80706ca8` at `80708554`. Setup changes
preview/capture state, waits, flags and other mode-specific state before invoking
wrapper `8022edac`, which calls `AppSetMode 80204460`. In the selected zero
setup branch, flag `+3e` in the runtime UI/capture-state object pointed to by
`808918a0` selects mode53. This is distinct from the recovered 38-byte persistent
view bank pointed to by `808918ac`. Otherwise runtime byte
`80891810` selects mode58 when nonzero or mode50 when zero; the mode58 arm clears
that byte afterward. Other setup branches select mode60 or mode50.

This is a source-traced capture arm. Its full event predicates and the physical
button/key source reaching it remain unresolved. The presence of mode50 is not
by itself a measurement of which branch the user's Auto-mode shutter uses.

`AppSetMode`'s 50/60-family switch maps modes as follows:

| Mode | Capture selector |
| --- | --- |
| `50` and reviewed family default | 0 |
| `53` | 1 |
| `55` | 3 |
| `58` | 6 |
| `60` | 2 |
| `61` | 5 |
| `62` | 7 |

The exact table at `80253e50` and selector-setting delay slots are checked.
The capture arm posts only when getter `8020b1c0` returns zero. The message is
pipe0/event `fffffff8`, action1, selector. StillServer `8023f458` routes the
request to `80239614`, which retains action/selector in shared state
`808c1bd8/808c1be4` and handles existing mode transitions. It can invoke
`80239494` immediately or defer work according to current state. Do not assume
every mode request immediately starts a new capture.

Action1 in `80239494` reaches `8032fad4`. Selectors 0/1/3/6 create
`StillCaptMain` at `80333458` with a 12,000-byte stack and the selector as thread
argument. Selector2 starts `Capture_Sequence` with argument0 and stack10,000;
selector5 uses its alternate thread-creation helper with argument1. Selector7
uses the same sequence entry with argument2 and stack8,000; selector4 starts
the separate DRAM path. These arguments are selectors, not external frame
pointers.

## Capture, creation and compression queues

The checked prefix window at `80333458` calls capture entry `80330d98` at
`80333594`. One branch in that entry posts the capture-object pointer as
argument0 on pipe0/event `1006`; cyclic/alternate branches use other events,
including `10000038`.

StillServer forwards event1006 through `80239fd4` to pipe4/event `1014`, retaining
the two argument words. The FileCreator loop at `8030980c` receives pipe4 messages
and invokes `8030847c` for event1014, using the received object pointer.

The creator processes the existing RAW/image state and then checks capture
byte `+2de`. Its final arm sets that byte to1 before posting the object to
pipe0/event `1044`. An already marked object skips that final post. The server
handles1044 with `8023a030`, which forwards the same arguments to pipe7/event
`1042`. The [saved-JPEG map](saved-jpeg-path.md) continues from FileCompressor's
1042 receive through StillImage, JPEG start/wait/destruction, EXIF assembly and
the asynchronous segment writer.

No caller-owned frame becomes safe to access just because its pointer passes
through these queues. Complete post-failure cleanup, cyclic paths and active
object/cache ownership remain unresolved.

## Queue-message ownership boundary

`801f5730` takes pipe, event and two argument words. It stages four stack words:
event, argument0, argument1, `ffffffff`, then calls queue-send `800cc868` with
wait argument `ffffffff`. Event `fffffffe` selects a queue at pipe object+40;
ordinary events use pipe object+8. The wrapper returns true for send status0;
an absent/disabled pipe reports a diagnostic and returns false.

The staged record contains pointer tokens and scalars. No deep copy of the
referenced capture buffer is established. Queue record handling, object
ownership transfer, receiver completion and memory visibility are separate
contracts. Internal event numbers are not PTP operations or a supported
device-command recipe.

## Remaining gate and reproduction

```powershell
python tools/map_shutter_route.py --output derived/shutter-route-check.json
python -m unittest discover -s tests -p test_shutter_route.py -v
```

The eight focused tests cover mode-family/default behavior, the runtime-state
gate, selector/thread distinctions, unsigned argument widths, queue-record
endianness/extent, urgent-queue selection and source rejection. They perform
no firmware execution or camera operations.

Still required: physical key/event producer and live Auto-mode branch evidence;
one chosen hook's exact pixel packing, stride, capacity and lifetime; complete
cache/DMA ownership; safe placement and hook ABI; custom controls and persistence;
complete installed backup and independent software recovery. The platform
remains blocked for executable camera trials.
