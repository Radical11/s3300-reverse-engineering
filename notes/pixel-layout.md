# JPEG selector and pitch boundaries

25 October 2026. This source-bound static follow-up separates two selectors
that must not become a guessed RGB/YUV adapter. It performs no camera request,
memory read, firmware patch or runtime processing. Its evidence is direct
Ghidra analysis, separately identified from REA Evidence.

The reproducible report is [pixel-layout.json](../evidence/pixel-layout.json),
generated by [map_pixel_layout.py](../tools/map_pixel_layout.py). The generator
checks the original firmware SHA-256 and authenticated analysis image, verifies
39 selected original instruction words, and checks all 3,254 instruction records
in four retained native dossiers against the decoded image.

## Two selectors, not one format value

The ApsJpeg argument at `8032b20c` has a u32 at `+4` and a separate u32 at `+8`.
It copies their low halfwords into the JPEG options structure at `+2` and `+4`.
Constructor `801a4490` then stores those fields separately in context `+da` and
`+dc`. The first is the JPEG input kind. The second also governs the wrapper's
address rebasing and later orientation-related geometry choices.

In StillImage `8031aa5c`, both reviewed create/go call sites, `8031b848` and
`8031b9f8`, explicitly write **zero** to ApsJpeg argument `+4`. Argument `+8`
comes from capture-object byte `+2d4`, retained through stack slots `44c` or
`414`. Consequently, a value of one in that capture byte does not mean these
branches pass JPEG input-kind one. The active Auto-mode branch and actual live
capture-byte value are still unobserved.

This refines the earlier [saved-JPEG map](saved-jpeg-path.md): its selector0/1
rebasing helper describes **ApsJpeg argument +8**, not a universal decoder for
the JPEG engine's input-kind field.

## What kind one establishes

The constructor's authenticated diagnostic identifies input-kind one as 420
input and says this hardware requires ICA conversion from 420 to 422. The
reviewed branch requires flag `40`, otherwise it calls the diagnostic failure
helper. Kind-one chroma descriptors also require even left/top coordinates.

The conversion path allocates and initializes another path through an indirect
factory. It is stateful and may adjust options/context. Neither the diagnostic
nor these selected guards proves component byte order, numeric range, complete
plane lengths, CPU access or live ownership. They are not sufficient guards for
a public camera call.

## DMA geometry is explicit but narrow

Helper `801a5c40(context, fields, frame, transfer_height)` computes the beginning
of an internal DMA description:

| Quantity | Reviewed computation |
| --- | --- |
| Horizontal block | Normally 16; flag `80` with secondary option `+dc != 1` selects 8 |
| Transfer-height quantity | Flag `80` forces 16; otherwise retains the caller argument |
| ROI width | Rounded up to the selected block and written back to descriptor `+14` |
| Parent byte-pitch arithmetic | Parent width when context input-kind `+da == 1`; otherwise low32 of twice parent width |
| Parent-pitch words | `low32(byte_pitch + 3) >> 2`, stored at DMA `+14` |
| Burst words | Block divided by 4 for kind one, otherwise divided by 2, stored at DMA `+0c` |

The descriptor's parent width, rather than its ROI width, supplies the pitch
arithmetic. Width rounding and word rounding preserve 32-bit wrap in the target.
The pure helper reports wrapping instead of treating such ranges as safe.
Later orientation/operation-dependent DMA fields, addresses and synchronization
are outside that helper's model. A zero ROI can reach a zero arithmetic result
in isolation even though the earlier constructor rejects zero image dimensions.

## Remaining gate

There is still no RGB8 camera adapter. Component order/range, selected active
frame extent, allocation lifetime, CPU/cache-line access and concurrent DMA
ownership must be established at one selected hook. A pitch-like arithmetic
quantity is not proof that a host algorithm may edit that memory. Safe code
placement, hook ABI, complete backup and independent recovery remain required.

Reproduce into a fresh path:

```powershell
python tools/map_pixel_layout.py --output derived/pixel-layout-check.json
python -m unittest discover -s tests -p test_pixel_layout.py -v
```

The ten focused tests cover the actual reviewed flag/alignment predicates,
separate selectors, parent-versus-ROI pitch, block selection, wrapping arithmetic
and source rejection. They do not emulate hardware or execute camera firmware.
