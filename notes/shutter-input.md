# Scanner and logical shutter events

25 October 2026. **Source-bound static input path; no camera-callable adapter.**
This follow-up extends [shutter-route.md](shutter-route.md) upstream into the
input scanner, debounce logic, host-message queue and UI mode dispatch. It never
reads hardware or sends an event. Physical key wiring, installed pad identity,
live polarity and current Auto-mode state have not been measured.

The reproducible report is [shutter-input.json](../evidence/shutter-input.json),
generated by [map_shutter_input.py](../tools/map_shutter_input.py). Original
firmware and decoded-image hashes are authenticated, 52 selected instructions
are checked independently with Capstone, and every imported instruction in 21
native dossiers is compared with original bytes. These are direct Ghidra/static
findings, separately labelled from REA Evidence.

## Register snapshots and normalized bits

Scanner `806a02bc` contains these explicit unsigned-word expressions:

| Read address | Expression | Normalized input bit |
| --- | --- | --- |
| `b0020448` | `(word == 0) << 1` | `0002` |
| `b002044c` | `word == 0` | `0001` |

The comparison is against the complete read word, not only its low bit. Later
mapping code and independent UI diagnostic consumers associate bit2 with SNAP1
and bit1 with SNAP2. This establishes source-level interpretation of these
sampled values. It is not a physical pin measurement or proof of electrical
switch polarity on the connected camera.

The same scanner also reconfigures and toggles GPIO matrix lines through
`800a1468`, `800a1580` and MMIO writes to sample other keys. A function called
for key status is therefore not automatically a passive read. No scanner or
GPIO entry was called on the device.

## Debounce acceptance and edge masks

`806a12b8` calls scanner/debouncer `806a109c` and repeat handler `806a0d04`.
Its periodic parent is `8069e4d4`. These runtime state fields are recovered:

| Address | Role |
| --- | --- |
| `808d7454` | Current sampled state, u16 |
| `808d7456` | Previous accepted state, u16 |
| `808d7458` | Enabled rising-edge mask, u16 |
| `808d745a` | Enabled falling-edge mask, u16 |
| `80818472` | Candidate changed state, u16 |
| `80818470` | Candidate pending flag, u8 |

A sample equal to the previous accepted state clears the pending flag without
emitting an edge. The first changed sample becomes the candidate. If the next
pending sample matches that candidate, it is accepted; if it differs, pending
is cleared and the previous state remains unchanged. A bouncing A/B/B sequence
does not immediately accept B: a new pair must be collected after the mismatch.

Accepted edge words are `~previous & current & rising_mask` and
`~current & previous & falling_mask`, restricted to 16 bits. The previous state
is updated even when the masks suppress all events. Initialization `806a0574`
sets rising mask0 and falling mask7000; mode lifecycle changes these masks.
Do not assume both SNAP press/release directions are initially enabled.

The report models scan-count behavior. A physical sampling interval or debounce
duration was not measured, and numeric timing expressions elsewhere do not
substitute for that measurement.

## SNAP events and host queue

Rising mapper `806a0b00` emits SNAP1 low ID2 for bit2, then SNAP2 low ID1 for
bit1. Falling mapper `806a09a4` emits low IDs12 and11 respectively. Poster
`806a065c` supplies host category100, producing combined IDs102/101/112/111.
The menu consumer `805ac03c` recognizes102 with a `MSG_KEY_SNAP1` diagnostic;
`806ff834` recognizes101 with a `Get SNAP2` diagnostic. Those diagnostics
corroborate the checked bit-to-event instructions rather than replacing them.

The poster has pending-key serialization. Some low key IDs are deferred in a
32-word ring at80816e08, with index80816e94 wrapped by1f. Pending-key count
80816e98 and prior key8081846a affect whether posting occurs immediately;
ID1 has a special count rule. The pure two-key mapper does not model FIFO
overflow, delivery ordering across all key combinations or all deferred state.

Host sender `80212b90` copies two scalar words into queue8010aba4, after its
readiness/filter checks. Queue creation `80212d28` specifies two message words;
sender overflow asserts. Receiver `80212edc` has an optional callback that can
consume/filter messages. It returns surviving category/ID words to UI receiver
`806aa198`, then processor `806a8a2c` and mode dispatcher `80740280`.

No image-buffer ownership is transferred by these scalar key messages.
Internal key IDs are not USB/PTP operations or a supported injection interface.

## View-state consumers and release limits

Mode dispatcher `80740280` combines category and payload with OR. UI mode
family2000 reaches `8073f858`; exact state2050 selects `80707590`, state2051
selects `80704598`, state2060 selects `806ff834`, and state2068 selects
`80707234`. These are runtime mode codes, not all synonyms for Auto mode.

In exact state2050, event101 reaches preparation arm807078d8. That arm can
transition to focus state2051 or take later branches according to runtime
capture/UI flags. A physical full press must not be described as an
unconditional direct call into JPEG compression.

Event112 in that handler clears byte36 in the runtime UI/capture-state object
pointed to by808918a0 and calls `806ff7fc`. That helper restores a temporary
selection from80891812 when80891843 is set, then clears the flag. The object is
distinct from the previously recovered 38-byte persistent view bank pointed to
by808918ac. Event111 does not enter the reviewed101/112 arms in this exact
handler. Other focus/capture states have separate handlers.

This narrows the release path but does not establish a universal safe
cancel-capture operation or prove all focus, burst and sequence cancellation
lifecycles. The downstream [capture-route map](shutter-route.md) retains the
later setup/mode/queue connection to JPEG processing.

## Reproduce and remaining gates

```powershell
python tools/map_shutter_input.py --output derived/shutter-input-check.json
python -m unittest discover -s tests -p test_shutter_input.py -v
```

Nine focused tests cover register-word interpretation, two-scan acceptance,
bounce rejection, pending cancellation, disabled edge masks, event order,
unsigned widths, state-specific routing and source rejection. They execute no
firmware and access no camera.

Required evidence still includes live scanner/mask/mode correlation, complete
focus/capture/release ownership, a selected frame hook's packing/stride/capacity
and cache ownership, safe placement and hook ABI, full installed backup and an
independent software recovery route. Executable camera trials remain blocked.
