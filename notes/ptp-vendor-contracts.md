# PTP vendor registration and access boundaries

25 October 2026. This follow-up examines the advertised vendor operations in
the authenticated supplied S3300 v1.1 application. It sends no PTP operation,
USB request, mode change or camera command. Direct Ghidra/Capstone findings
are separate from REA Evidence and exact installed-image identity is unknown.

The reproducible report is
[ptp-vendor-contracts.json](../evidence/ptp-vendor-contracts.json), generated by
[map_ptp_vendor_contracts.py](../tools/map_ptp_vendor_contracts.py). It checks
selected original instruction words and every imported instruction in 15 native
dossiers before interpreting registrations. Reproduce into a fresh path:

```powershell
python s3300.py research-map ptp-vendor derived/ptp-vendor-check.json
python -m unittest discover -s tests -p test_ptp_vendor_contracts.py -v
```

## Dynamic registry

The table pointer at `80898e7c` refers to 256 records of 12 bytes. Lookup
`8077f050` compares an unsigned 16-bit opcode. Insertion `8077f108` searches
for the first opcode-zero slot and stores these fields:

| Offset | Field |
| --- | --- |
| `0` | opcode, u16 |
| `2` | local/queued route, u8 |
| `3` | disabled flag, u8 |
| `4` | data phase, u32 |
| `8` | handler address, u32 |

Initializer `8077f204` allocates/zeros `c00` bytes and installs standard handlers.
Higher-level registration updates an existing opcode or inserts a new record.
This is runtime state, not a static firmware table that can be read at its
runtime pointer from the update image.

Command dispatcher `80779e00` performs session/transaction checks, rejects
unsupported/disabled records, then uses the route and data-phase fields. The
queued route posts event `8800` to the application. A shared transport function
does not make this dispatcher equivalent to the separate debug agent.

## Advertised operations

| Operation | Recovered registration and behavior | Access implication |
| --- | --- | --- |
| `9002` | Application `8057ac40` registers local handler `8057db04`, phase 1. Parameter 1 with nonzero state byte `8065ebdd` calls `8063b3bc(0)`; parameter 2 with zero state calls it with 1. That endpoint calls capture/display-related routines, sleeps and updates state. | Data-in registration does not imply read-only behavior. |
| `9003` | Registered on queued route 1 with no local handler. HCE consumer `80634c18` recognizes `9002`/`9003` and acknowledges through `8063b85c`. | No arbitrary memory-read contract established. |
| `9005` | Initializer assigns handler `80781028`, also used by standard `100c`, phase 2. | Object-upload path; no passive diagnostic semantics established. |
| `9006` | Initializer assigns handler `807815a0`, also used by standard `100d`, phase 0. | Object-upload path; full write behavior is outside this map. |

`8057db04` contains another branch for `9003` that changes settings, but the
reviewed application registers that opcode on the queued route. Do not describe
the unselected local branch as the observed active implementation. The two
object-upload addresses are interior labels in retained Ghidra functions;
registration identity is checked without inventing new function boundaries.

The exact user-facing purpose of the `9002` state switch remains inferred.
The state-changing calls and lack of a safe memory-read contract are sufficient
to keep it outside the read-only camera allowlist.

## Emulation scope and failed analysis

The report distinguishes synthetic instruction tests from static registration
recovery. The initial attempt to execute the entire initializer under pinned
Unicorn 2.1.4 raised an unhandled CPU exception at the backward branch
`8077f444`, despite authenticated matching instruction bytes. A JR host-stub
attempt also failed. These are host harness/engine limitations, not evidence
that the camera firmware fails there. They cannot be reported as a successful
initialization or silently replaced with guessed live values. The report
records the narrower emulation that actually completes, its synthetic inputs,
any host stubs and its exclusions. Static instruction and dossier checks remain
independent of that emulation result.

The passing fallback executes original insertion/lookup instructions against
a host-seeded table. It checks the last slot, flag-byte truncation, full-table
rejection and five local `9002` packet cases with the state endpoint stubbed.
It executes 5,686 instructions in the verified run. Application registration
is explicitly not executed. A synthetic sentinel instruction is used after
returns to avoid stale Unicorn branch state across calls; no original
instruction is changed. Those tests support the helper layout and branch
semantics, not live table contents or successful full initialization.

## Remaining route and recovery gate

The search covers these selected registrations, the command dispatcher, local
`9002` handler and HCE consumer. It is not a whole-program proof that no other
vendor request exists. No reviewed operation here establishes a safe bridge to
ConfigMem/GetMem, whose normal application debug path uses different mode and
handler registrations. Safe installed memory ranges, bounded access, complete
flash/calibration/ECC backup coverage and independent software recovery remain
unverified. No new operation was added to the camera allowlist.
